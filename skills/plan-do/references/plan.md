# Planning decisions

Status: proposed starting method. Anik's preferred planning format and estimation habits are not yet established.

Translate the requested outcome into work that can be executed and reviewed. Read the repository and its project instructions for an existing codebase. Preserve any agreed MVP brief and acceptance criteria instead of rediscovering the product for a narrow feature.

For the client-product paths captured in the coordinator's [product method](../../loop-zero-to-production/references/product-method.md), use the reference adaptation map or client issue map as planning input. Include agreed content, branding, sections, and user flows in acceptance criteria when they are part of the client's request. A functioning backend alone may not satisfy a reference-led deliverable. Do not infer the plan's feature list from a project name.

## Make the plan useful

- Establish what completion means in observable behavior.
- Identify dependencies and decision points that could change the work.
- Resolve routine choices from project conventions and evidence. Give Anik a recommendation when a trade-off materially affects scope, architecture, cost, or delivery.
- Organize larger work into verifiable increments. Choose the level of detail based on uncertainty and task size, rather than imposing a fixed phase count.
- Identify where data changes, integration behavior, authorization, or deployment constraints require extra care.
- Label assumptions. Do not fabricate estimates, business requirements, deployment targets, or missing repository files.

For a backend choice without an established stack, start from Anik's Laravel preference. If the project is Node/React, plan within that stack. Ask about hosting only when it matters and has not already been established.

## Reviewable output

For substantial work, show the goal, acceptance criteria, recommended approach, ordered increments, material risks, validation, and unresolved decisions. Record alternatives only when they explain the recommendation.

A plan should make the next action clear. Producing a plan does not by itself authorize implementation, purchasing, publishing, or deployment. If implementation is requested, continue with [Labour](../../labour/SKILL.md) within that scope.

When [loop-zero-to-production](../../loop-zero-to-production/SKILL.md) owns an end-to-end task, planning is an intermediate result. Preserve context through [the shared handoff](../../loop-zero-to-production/references/handoff.md) and continue into the next requested stage without asking whether to do already authorized work. A planning-only request still finishes at its plan.
