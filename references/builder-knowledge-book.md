## Why it is not a rule source

It is a bibliography, not a method. It names what to read; it does not say what to do when a
consumer receives a duplicate message or when a client asks for a countdown timer. The
library's own capabilities carry that, and a link list cannot be verified into one.

The value it does have is orientation — knowing that a named work exists for a problem. That
is what this file preserves.

## Citation defects found in the received sections

Three, all in the links themselves. They are the reason the document is not treated as a
citable source:

- **CAP "Twelve Years Later" misattributed to Gilbert & Lynch.** That article is Eric
  Brewer's, *IEEE Computer*, 2012. Gilbert and Lynch wrote the 2002 proof of the conjecture —
  a different paper. Citing the wrong author of the best-known correction to CAP is the kind
  of error that is noticed.
- **"Kafka paper" links a Confluent marketing blog.** The paper is Kreps, Narkhede and Rao,
  *Kafka: a Distributed Messaging System for Log Processing*, NetDB 2011. A vendor blog post
  is not the paper and does not carry its claims.
- **§1 Articles cell is a bare `google.com/search?q=` placeholder.** An unfilled slot shipped
  as if it were a citation.

A generated bibliography is a plausible-looking list; plausibility is what generation
optimizes for. Verify any entry before it leaves this machine.

## If a deep-research pass is ever proposed on it

It was considered and rejected. A curated link list contains almost nothing falsifiable — the
adversarial verification phase has no claims to attack, so the run costs a lot and returns a
restatement of the list. What is worth running instead is narrow and mechanical: check every
link resolves, and check each named work's author, venue and year against the linked target.
That finds this file's three defects and any like them.
